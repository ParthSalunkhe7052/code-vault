## Introduction

The current Cloud Build testing infrastructure relies on isolated Python scripts that do not accurately mimic the `multipart/form-data` requests generated by the React frontend. This has led to "works in test, fails in prod" scenarios. We need a simulation harness that runs the full stack locally and replays the exact user interaction via API calls.

## Problem Statement

**Current Process:** Developers manually upload files via the UI to test, or run isolated Python scripts that use clean `requests.post` calls which differ from browser behavior.
**Primary Users:** Backend Engineers, Pickle Rick.
**Pain Points:** 
- Discrepancy between `requests` lib and browser `FormData`.
- Manual testing is slow.
- "Cloud Build" workflow fails when initiated from UI due to header/boundary mismatches.
**Importance:** Critical. The core feature of the platform (building code) is unreliable.

## Objective & Scope

**Objective:** Create a single-command E2E harness that verifies the entire Cloud Build pipeline using the actual frontend payload structure.
**Ideal Outcome:** A script that:
1. Starts the backend and frontend (if needed).
2. Sends a payload identical to the React app's upload.
3. Polls for success.
4. Identifies the root cause of failures.

### In-scope
- Python script to launch `main.py` (Backend).
- Python script to construct `multipart/form-data` request using `TestBot.zip`.
- Polling logic for build status.
- Integration into the Pickle Rick fix loop.

### Not-in-scope
- Browser automation (Selenium/Playwright) - explicitly rejected in favor of API Replay.
- UI visual regression testing.

## Product Requirements

### Critical User Journeys (CUJs)
1. **The Ghost User**: 
   - The Harness starts the backend server in a background process.
   - The Harness loads `C:\Users\parth\OneDrive\Desktop\Code Vault\TestBot\TestBot.zip`.
   - The Harness constructs a POST request to `/api/cloud-build` (or relevant endpoint) with exact headers mimicking the React Client (Boundaries, Auth Tokens).
   - The Harness polls the build status endpoint until `SUCCESS` or `FAILURE`.
   - The Harness outputs the logs.

## Assumptions

- The `TestBot.zip` is a valid project file.
- The backend is runnable via `server/main.py` or similar.
- We can determine the correct API endpoint by reading the frontend source code.

## Risks & Mitigations

- **Risk**: Port conflicts if server is already running. -> **Mitigation**: Check ports 8000/3000 before starting, or kill existing processes.
- **Risk**: Auth required. -> **Mitigation**: The harness might need to generate a dev token or bypass auth for localhost.

## Business Benefits/Impact/Metrics

**Success Metrics:**
- **Reliability**: Cloud Build works 100% of the time from the UI.
- **Debug Time**: Reduced from minutes (manual) to seconds (automated).
